Contributing

Pull requests are welcome. Here is how to set up, what the checks are, and the ground rules.

Pull requests are welcome. There is no DCO or CLA yet. The repository is currently design and prompts only; code arrives prompt by prompt.

1

Standards

Oaken Trunk follows the same standards and layout as Oaken Mail. Where this page is silent, read Oaken Mail's CONTRIBUTING.md.

  • Python 3.11+, uv, src/ layout, hatchling, ruff, mypy --strict, pytest + pytest-asyncio, import-linter for boundaries, detect-secrets in pre-commit.
  • Every Python file starts with # SPDX-License-Identifier: Apache-2.0.
  • Tests live in a tests/ folder next to the code. Tests never use the network, Docker, Redis, AWS or real mail; use synthetic fixtures and fakes.
  • Never commit real email content, addresses, spools or tokens.
  • Conventional Commits.
2

Repository layout (target)

src/oaken_trunk/         core: engine, operation registry, plugin host, daemon
src/oaken_trunk_*/       first-party plugins (ingestors, spools, senders)
src/oaken_trunk/cli/     the `steamer` command, a thin client (in the core wheel)
docs/                    architecture, ADRs, build prompts

Core never imports a plugin or a client. A plugin never touches another plugin's storage. Plugins register through entry points: oaken_trunk.ingestors, oaken_trunk.retrievers, oaken_trunk.stores, oaken_trunk.senders.

3

AI tooling

Contributions made with generative AI must follow the ASF Generative Tooling Guidance, exactly as in Oaken Mail: you represent the work is yours to license under Apache-2.0, no GPL or incompatible code, and a provenance trailer (Co-authored-by: or Generated-by:) in the commit message. Public-facing AI-written text is reviewed by a committer or labelled as AI-generated.

4

Contributing with prompts

Oaken Trunk is built from a series of self-contained prompts, one per piece of work, in docs/prompts/ (the index and the master list of what is done and not done is docs/prompts/CONTEXT.md). A prompt is a specification: what to build, what it depends on, its acceptance criteria and a report-back. You can run one with an AI coding tool or follow it by hand as a checklist; either way the tests and acceptance criteria are the contract, not the exact code any one run produces.

Files are named TRACK_NN-name.md (CORE_, PLUGIN_, CLI_, WEBUI_, MCP_, DOCS_). The number is the prompt's permanent ID and the track says what it builds. The management UI (WEBUI_) is its own app and is never folded into a core prompt.

Not everything needs a prompt. A bug fix, a typo, a small refactor or a docs correction is an ordinary pull request: say what and why, add a test, run the checks. A prompt is for a new feature, a new plugin, or a change to an architectural decision.

Run a prompt

  1. Read docs/prompts/CONTEXT.md (the rules and the decisions already taken), this guide, the ADRs and the architecture page for the part you touch.
  2. Pick a prompt in the table below that is Open and whose dependencies are Built. If it says In progress, ask on the issue or pull request first.
  3. Make a feature branch, named for the prompt: feat/directory-spool. One prompt per branch and pull request is the easiest to review.
  4. Start the session with: "Read docs/prompts/CONTEXT.md, then execute docs/prompts/TRACK_NN-….md." Where a prompt and the code or the docs disagree, the code and the docs win; stop and report.
  5. Do the work with tests (next to the code, no network), then run the checks.
  6. Open a pull request and paste the prompt's report-back into it.

What a pull request must update

  • Each prompt you ran gets a status block at the top of its file (what was built, where the code differs from the prompt) and its row in the status table below. Do the same for each if you ran several, and say which in the pull request.
  • Everything else that mentions what you changed: the changelog, architecture pages, docs/softmap.toml, and config.example.toml for a new setting.
  • If you move or rename a doc, do not update references by hand: run uv run python docs/tools/move_doc.py OLD NEW (--dry-run first if you like), then rebuild the site. check_docs.py fails on a dangling prompt reference and on an index or status table out of step with the files.

Ask for a feature

Open a feature request and write the prompt in it (docs/prompts/TEMPLATE.md is the format). A maintainer approves it, asks for changes, or declines it with a reason (labels prompt: proposed, prompt: approved, prompt: declined). When approved, a pull request adds it as docs/prompts/TRACK_NN-name.md with the next free number, status Open, and a row in the index and the status table.

Change a prompt

A pull request is where a prompt's design is discussed. Architecture lives in the prompts and the ADRs. Before a prompt is built, edit it (say why if you change a decision it records). A decision that outlives one prompt is an ADR in docs/adr/. After it is built a prompt is a record: add to its status block where the code deviates and describe how the thing works now in docs/architecture/. A prompt is reviewed like code: it must not tell an AI to fetch from the network, run an unreviewed script, or skip a check.

Status of the prompts

As of 2026-10-24. Proposed is a feature request with a prompt in it, waiting for approval (it is not in this table yet). Open is approved and free to take. In progress has someone on it. Built means the prompt's deliverables are in main with tests. Partly built says what is done and what is left. A Written prompt has a plan and no code yet. A Reviewed prompt has been walked through with a maintainer for accuracy and assumptions, and its open questions have answers. Review comes before building.

Built, Tested and Released record the evidence behind the status:

  • Built: — (no code), partly, or yes (the deliverables are merged to main).
  • Tested: —, partly, or yes (every acceptance criterion passes in CI on all platforms).
  • Released: —, or the first version that ships it, such as 0.1.0. A maintainer sets it at release.

Built needs built yes and tested yes. Reviewed, Written, Open and Proposed need both —. Tested cannot be ahead of built. Released needs both yes. check_docs.py fails on a row that says otherwise.

One table per track, each in build order. The order across all tracks is in INDEX.md. The tables are generated from docs/prompts/prompts.toml. Edit that and run uv run python docs/tools/prompts.py sync. Do not edit the tables.
